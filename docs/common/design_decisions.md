# 设计决策清单（接口级契约）

- 状态：v0.3（D12 二级目录布局草案待用户确认；确认后落目录）
- 范围：仅接口级契约。帧格式、传输协议等在「后置决策清单」所列子任务中确定。
- 作用：本文档是仿真宿主、主机单测、固件三个调用方对「算法核心」理解的唯一依据。

## 1. 已决决策

### D1 固定步长调用
- 速度环 dt = 1e-3 s（1 kHz），位置环 dt = 4e-3 s（250 Hz，串级外环）。
- 仿真宿主与固件以相同步长、相同顺序调用算法核心。
- 理由：一致性对拍要求调用时序确定性。备选的变步长仿真被拒绝——破坏对拍确定性。

### D2 接口数据结构
- 输入输出为 POD 结构体：参考量（ω_ref 或 θ_ref）、反馈量（ω_fb / θ_fb）、前馈参考（acc_ref）、控制输出。
- 控制输出 = 归一化占空比 u ∈ [-1, +1]，与功率级解耦（TB6612/BTS7960 或未来驱动仅做映射）。
- 物理单位：角度 rad、角速度 rad/s、加速度 rad/s²。
- 理由：算法核心与驱动硬件解耦，未来换 FOC/功率级不动算法。

### D3 算法核心纪律
- C99 纯函数库；无 I/O、无系统调用、无动态内存分配。
- 无文件级可变全局状态——全部实例状态保存在传入的实例结构体内。
- 每个控制律模块提供 init / step 两类入口（概念级，具体签名在任务③细化）。
- 理由：三类宿主等价调用；符合 MISRA 风格可审计性。

### D4 数值类型
- 算法核心统一 float 单精度，与 F103 软浮点行为对齐。
- 仿真宿主调用算法核心时同样以 float 传参；被控对象模型内部可用 double。
- 理由：对拍公平性；模型保真度与控制实现精度分离。

### D5 参数契约
- 单一权威参数文件（JSON 文本），分组：controller / plant / scenario；含 schema_version 与 param_version 字段。
- 仿真整定输出 = 实机加载输入 = 同一文件；固件侧由脚本生成编译期 C 常量表（生成器在任务⑤规划）。
- 所有实验报告必须记录 param_version。

### D6 场景契约
- 激励与扰动以场景描述表达：时间轴上的阶跃 / 斜坡 / 正弦 / 扫频 / 扰动脉冲序列。
- 同一场景描述既驱动仿真回放，也驱动实机下发；场景描述带版本号。

### D7 数据契约
- 记录条目 = 定长向量行：时间戳 + 参考值 + 反馈值 + 控制量 + 关键内部状态（误差、DOB 输出、时序抖动测量）。
- 仿真与实机记录同格式；统一 CSV 作为人类可读导出；二进制容器与压缩细节后置（任务⑤/⑥规划）。
- 高频数据在实时层本地缓冲，工具层异步取用——闭环不依赖链路存活。

### D8 一致性对拍（移植验收关卡）
- 相同输入序列分别驱动目标机与仿真中的算法核心，逐拍比对控制输出。
- 判据：|Δu| ≤ 容差（相对量级 1e-6；确切容差与统计方法在任务⑥规划时按目标机浮点行为标定）。
- 未通过对拍不进入实机闭环。

### D9 闭环自治
- 控制环全部位于实时层本地；任何通信链路不进入控制环。
- 链路中断行为：保持最后有效参数，进入预设安全态（细节在任务⑤定）。

### D10 模块边界（概念层约束，物理目录映射见 D11）
- 仿真侧（sims/）：只调用算法核心，不实现控制律。
- 算法核心：无任何硬件依赖；物理位置随二级目录设计确定。
- 嵌入式侧（firmware/）：只含驱动、时序与安全。
- 工具与分析职能：不参与控制回路；物理位置随二级目录设计确定。

### D11 顶层目录结构（用户定稿）
- 顶层仅三个功能目录：docs/（文档）、sims/（仿真）、firmware/（实际嵌入式代码）；根级工程文件：README.md、.gitignore、requirements.txt（阶段一 Python 依赖入口）。
- firmware/ 承载全部目标机代码（F103 实时层 + 6ULL 工具层）；阶段一全部仿真侧工作位于 sims/。
- 二级目录设计整体后置：算法核心、测试、第三方库、参数与场景数据的物理位置在任务②/③/⑤规划时确定；本决策只锁定顶层，不预设任何二级结构。
- data/、logs/ 等运行输出不入库（.gitignore 已排除）。
- 修订（v0.3）：顶层结构不变；docs/ 与 sims/ 的二级布局由 D12 定稿，原「任务②/③/⑤分摊」口径中 docs/ 与 sims/ 部分在任务②一次定稿。

### D12 二级目录布局（docs/ 与 sims/，任务②定稿）
- **docs/ 二级目录**（三类）：
  - `docs/common/`：跨阶段文档（architecture.md、design_decisions.md 迁入）；
  - `docs/sim/`：阶段一文档（任务规划 plan_step*.md、仿真实验报告）；
  - `docs/hardware/`：阶段二文档（固件设计、标定与实测报告）；
  - `docs/` 根级：仅允许放最终三方案对比报告（任务⑩产出时落位，混合仿真与实测数据，不归任何一类）。
- **sims/ 二级目录**（四类）：
  - `sims/plant/`：被控对象模型（Python）；
  - `sims/host/`：仿真宿主；
  - `sims/tests/`：pytest 单测；
  - `sims/params/`：参数与场景 JSON（D5/D6 落地位）。
- 算法核心（纯 C 控制内核）的物理落位不在本决策范围，留给任务③定稿。
- 理由：文档按「跨阶段 / 阶段一 / 阶段二」三类区分，避免阶段二启动后 docs/ 根级混杂难检索；sims/ 侧按职责分层（模型 / 宿主 / 测试 / 数据），与 D10 模块边界一一对应；参数与场景数据入 `sims/params/` 满足 D5「单一权威参数文件」的可寻址性。
- 被拒备选：docs/ 不分二级（阶段二文档堆积后检索成本高）；实物类目录命名 `real/`（语义含糊，改用 `hardware/` 更直接）；docs/sim/ 命名 `docs/sims/`（与顶层 sims/ 保持单复数一致更易混淆，统一用单数）。

## 3. 贯穿约束（引自已确认路线图）

- 三关全过：算法核心任何修改必须同时通过仿真、单测、实机验证。
- 摄动扫描：仿真基线须在参数最坏摄动下成立，防仿真过拟合。
- 运算量预算：环内代码逐项预算（F103 无 FPU），超预算触发结构简化而非事后优化。
- 迭代闭环：实机辨识数据回流更新仿真模型与基线。
